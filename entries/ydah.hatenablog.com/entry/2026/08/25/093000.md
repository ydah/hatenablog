Linuxのseccomp user notificationをRubyから扱うためのBindingとして、`seccomp-notify` というGemを作りました。

[https://github.com/ydah/seccomp-notify:embed:cite]

このGemを作るきっかけになったのは、2026年8月22日に開催された[Kernel/VM探検隊@東京 No19](https://kernelvm.connpass.com/event/395390/)で聞いた、[@nullpo_head](https://github.com/nullpo-head)さんの「動的にallow/denyできる ファイルサンドボックスを作る」という発表です。

[https://speakerdeck.com/nullpo_head/deny-dekiru-o-tsukuru:embed:cite]

発表では、Seccomp-BPF、Namespace、LandlockといったLinuxのサンドボックス技術が整理されていました。その上で、seccomp user notificationを使い、ファイルアクセスの判断を別プロセスへ委譲する仕組みが紹介されていました。

通常のSeccomp-BPFでは、システムコール番号や整数の引数を使って許可や拒否を決められます。一方で、`openat(2)` に渡されたファイルパスや、`connect(2)` に渡された接続先のように、ポインタの先にあるデータをフィルターから読むことはできません。

seccomp user notificationでは、対象のシステムコールを実行前に止め、listener FDを持つ別プロセスへ通知できます。通知を受け取った側は、対象プロセスのメモリなどを調べた上で、システムコールを続行する、エラーを返す、元の処理を実行せずに戻り値を返す、といった応答ができます。監視プロセス側で開いたファイルディスクリプタを対象プロセスへ渡すこともできます。

発表を聞きながら、これをRubyから扱えたら面白そうだと思いました。テスト中の外部通信を止める、プログラムが開こうとしたファイルを確認する、OSとの境界で意図的にエラーを返す、といった使い方ができそうです。

## seccomp-notifyとは

`seccomp-notify` は、Linuxのseccomp user notificationをRubyから扱うためのGemです。

主な機能は次のとおりです。

- 通知または拒否するシステムコールをRubyで指定する
- フィルターを設定した対象プロセスを起動し、監視プロセスをフィルターの外側に残す
- システムコールの通知をRubyのハンドラーで受け取る
- 対象プロセスから文字列、バイト列、ソケットアドレスを読む
- 指定した `errno` を返してシステムコールを失敗させる
- 元のシステムコールを続行する
- 元のシステムコールを実行せず、成功したように戻り値を返す
- 監視プロセス側のファイルディスクリプタを対象プロセスへ渡す
- 利用できるカーネル機能を実行時に確認する

C拡張やlibseccompには依存せず、Ruby標準添付の `Fiddle` からLinuxのカーネルAPIを呼び出しています。現在はLinuxのx86_64とaarch64、Ruby 3.1以降を対象にしています。

`seccomp-notify` は、seccomp user notificationをRubyから利用するための部品であり、セキュリティポリシーや完成したサンドボックスではありません。対象メモリを確認してから元のシステムコールを続行するまでの間にデータが書き換えられる[TOCTOU](https://jvndb.jvn.jp/ja/cwe/CWE-367.html)などの注意点があります。

[https://www.kernel.org/doc/html/latest/userspace-api/seccomp_filter.html:embed:cite]

[https://man7.org/linux/man-pages/man2/seccomp_unotify.2.html:embed:cite]

## インストール

インストールは通常のGemと同じです。プロジェクトへ追加する場合は、`bundle add` を使います。

```console
bundle add seccomp-notify
```

もちろん、グローバルにインストールして使うこともできます。

```console
gem install seccomp-notify
```

基本的なuser notificationにはLinux 5.0以降が必要です。元のシステムコールを続行する `CONTINUE` にはLinux 5.5以降、ファイルディスクリプタの注入にはLinux 5.9以降が必要です。

ただし、カーネルの機能はバックポートされることがあります。また、コンテナランタイムのseccompプロファイルによって、ホストのカーネルが対応していても利用できない場合があります。そのため、`seccomp-notify` はカーネルのバージョン文字列だけではなく、現在の環境で各機能を実際に利用できるか確認します。

## seccomp-notifyを使う

### まずシステムコールを止める

分かりやすい例として、`curl` のネットワークアクセスを拒否してみます。

```ruby
require "seccomp/notify"

policy = Seccomp::Notify::Policy.new do
  notify :connect, :sendto
end

supervisor = Seccomp::Notify.spawn(policy) do
  exec("curl", "https://example.com")
end

supervisor.on(:connect) do |request|
  request.error!(Errno::ENETUNREACH)
end

supervisor.on(:sendto) do |request|
  request.error!(Errno::ENETUNREACH)
end

status = supervisor.run
```

`curl` が `connect(2)` または `sendto(2)` を発行すると、カーネルは元のシステムコールを実行する前に対象スレッドを停止します。通知を受け取ったRubyのハンドラーは `ENETUNREACH` を返すため、元のシステムコールは実行されません。

対象にしているのは、アプリケーションのHTTPクライアントではなく、実際にLinuxへ到達したシステムコールです。そのため、Rubyのライブラリだけではなく、C拡張や子プロセスが発行したシステムコールも、フィルターの継承範囲内で対象になります。

`Seccomp::Notify.spawn` では、子プロセスへフィルターを設定し、親プロセスはフィルターの外側に残して通知を処理します。監視プロセスまで同じフィルターの内側へ入れると、通知を処理するために必要なシステムコールまで止めてしまう可能性があるためです。

### 接続先やファイルパスを確認する

すべての `connect(2)` を拒否するだけなら、通常のSeccomp-BPFでも実現できます。

seccomp user notificationでは、対象プロセスへ渡された `struct sockaddr` を読み、接続先を確認してから応答できます。

```ruby
supervisor.on(:connect) do |request|
  address = request.read_sockaddr(
    request.args[1],
    request.args[2]
  )

  loopback = address.ip? &&
    ["127.0.0.1", "::1"].include?(address.ip_address.split("%", 2).first)

  if loopback
    request.continue!(unsafe: true)
  else
    request.error!(Errno::EPERM)
  end
end
```

この例では、`127.0.0.1` と `::1` への接続だけを続行し、それ以外の接続を拒否しています。IPアドレスだけではなく、ポート番号やUnix domain socketのアドレスを確認することもできます。

同じように、`open(2)` や `openat(2)` の通知から、対象プロセスが開こうとしているパス文字列を読めます。

```ruby
policy = Seccomp::Notify::Policy.new do
  notify :openat
end

supervisor = Seccomp::Notify.spawn(policy) do
  exec(*ARGV)
end

supervisor.on(:openat) do |request|
  path = request.read_string(request.args[1])
  warn "openat: #{path}"
  request.continue!(unsafe: true)
end

supervisor.run
```

この例を使えば、ビルドが開こうとしたファイルを調べたり、テスト中に想定外の設定ファイルへアクセスしていないか確認したりできます。

`seccomp-notify` は対象プロセスのメモリを読んだ後、通知IDがまだ有効であることを確認します。ただし、通知が有効であることと、読んだメモリの内容がその後も変化しないことは別です。

対象メモリを読んだ後に `continue!` を呼ぶと、別スレッドが検査済みの文字列を書き換えてから元のシステムコールを実行させる可能性があります。`unsafe: true` は、この危険を理解した上で続行することを示し、警告を抑えるための指定です。この指定によって処理が安全になるわけではありません。

### 元のシステムコールを実行せずに応答する

通知されたシステムコールには、主に以下の応答ができます。

| メソッド | 動作 |
| --- | --- |
| `error!(Errno::EPERM)` | 元のシステムコールを実行せず、指定した `errno` を返す |
| `continue!` | カーネルに元のシステムコールを実行させる |
| `allow!(value)` | 元のシステムコールを実行せず、成功した結果として戻り値を返す |
| `add_fd!(io)` | 監視プロセス側のファイルディスクリプタを対象プロセスへ渡す |
| `kill!` | 通知を発行したプロセスを終了させる |

`allow!` は、元のシステムコールをそのまま許可するという意味ではありません。元の処理を実行せず、成功したように戻り値だけを返します。元のシステムコールを実行する場合は `continue!` を使います。

この仕組みを使うと、`connect(2)` に `ETIMEDOUT` を返したり、`openat(2)` に `EACCES` を返したりして、障害時の動作を確認できます。アプリケーションごとのモックを追加せず、OSとの境界で失敗を発生させられます。

もちろん、システムコールの戻り値にはそれぞれ意味があります。成功値を適当に返すと、対象プロセスを不整合な状態にする可能性があります。`allow!` は任意の処理を安全に無視する機能ではなく、戻り値の意味を理解した上でエミュレートするための機能です。

### ファイルディスクリプタを差し替える

seccomp user notificationでは、監視プロセス側のファイルディスクリプタを対象プロセスへ注入できます。

リポジトリには、対象プロセスが `/dev/urandom` を開こうとした場合に、別のファイルを渡す例を置いています。

```ruby
require "seccomp/notify"

replacement = File.expand_path("replacement.bin")
open_syscalls = RUBY_PLATFORM.include?("x86_64") ? %i[open openat] : %i[openat]

policy = Seccomp::Notify::Policy.new do
  notify(*open_syscalls)
end

supervisor = Seccomp::Notify.spawn(policy) do
  exec(*ARGV)
end

handler = proc do |request|
  path_argument = request.syscall == :open ? 0 : 1
  path = request.read_string(request.args[path_argument])

  if path == "/dev/urandom"
    File.open(replacement) do |file|
      request.add_fd!(file)
    end
  else
    request.continue!(unsafe: true)
  end
end

open_syscalls.each do |syscall|
  supervisor.on(syscall, &handler)
end

supervisor.run
```

対象プロセスが `open(2)` または `openat(2)` を発行すると、監視プロセスが代わりに `replacement.bin` を開きます。そのファイルディスクリプタを対象プロセスのFDテーブルへ追加し、追加されたFD番号を戻り値として返します。

対象プロセスから見るとファイルを開く処理が成功していますが、実際に渡されているのは監視プロセスが用意した別のファイルです。

この機能を使うと、テスト中だけ特定のファイルを固定した内容へ差し替えたり、対象プロセスへ直接ファイルを開かせず、別プロセスが開いたFDを渡したりできます。

[@nullpo_head](https://github.com/nullpo-head)さんの発表で紹介されていたCage Boxでも、Landlockで対象プロセスからのファイルアクセスを制限していました。その上で、ブローカーが代わりにファイルを開き、そのFDを対象プロセスへ注入していました。

[https://github.com/nullpo-head/cage-box:embed:cite]

私が面白いと思ったのは、処理を別のプロセスへ移し、その結果を対象プロセスへ返せるところです。単にシステムコールを許可または拒否するだけにとどまりません。

### seccomp-notifyを使ってできること

ここまでの機能を組み合わせると、たとえば以下のような用途に使えます。

- 選んだシステムコールを表示する小さなトレーサーを作る
- テスト中の外部ネットワークアクセスを拒否する
- プログラムが渡したファイルパスや接続先を記録する
- 指定した `errno` を返して障害時の動作を確認する
- ファイルやソケットを別のFDへ差し替える
- 対象プロセスの代わりに別プロセスが処理を行うブローカーを作る
- パッケージのインストールやビルド中に発生した副作用を調べる

Bindingとしては、これらを組み立てるための低レベルな機能を提供しています。

## seccomp-notifyの実装

`seccomp-notify` はRuby標準添付の `Fiddle` から `seccomp(2)`、`prctl(2)`、`ioctl(2)`、`poll(2)` などを呼び出しています。カーネルとやり取りする構造体は、Rubyの `String#pack` と `String#unpack` で表現しています。

通知対象を選ぶ[cBPF](https://docs.kernel.org/bpf/standardization/instruction-set.html)プログラムもRubyで生成しています。フィルターの先頭でアーキテクチャを確認し、x86_64ではx32 ABIのシステムコールを拒否します。`openat(2)` の書き込みフラグなど、整数引数で絞り込めるものは、ユーザー空間へ通知する前にcBPF側で確認できます。

対象プロセスがフィルターを設定して取得したlistener FDは、Unix domain socketの `SCM_RIGHTS` を使って監視プロセスへ渡します。また、カーネルが対応している `CONTINUE` やFD注入などの機能を、隔離した子プロセスで実際に試して検出しています。

Bindingの実装について詳しく書くと、とんでもない分量になりそうなので、この程度にしておきます。

## seccomp-notifyを使って作ったStraycall

RubyやRailsのアプリケーションでは、テスト中にデータベースへ接続したり、`tmp` や `log` へファイルを書き込んだり、必要なコマンドを子プロセスとして起動したりします。もちろん、それぞれの処理には必要な理由があります。

一方で、依存ライブラリの変更や設定の見落としにより、意図しない外部通信やファイル書き込み、コマンド実行が入り込むこともあります。こうした副作用を見直すために、`seccomp-notify` を使って `Straycall` というGemを作りました。

[https://github.com/ydah/straycall:embed:cite]

Straycallは、Rubyのビルドやテストが発行したシステムコールを監視し、意図していないネットワークアクセス、ファイルアクセス、コマンド実行を報告または拒否するCLIです。

Straycallでは、`seccomp-notify` の次の機能を使っています。

- `connect(2)` や `sendto(2)` などの通知から接続先を読む
- `open(2)` 系の通知からファイルパスを読む
- `execve(2)` と `execveat(2)` の通知からコマンド実行を検出する
- 通知されたシステムコールを続行するか、`errno` を返して拒否する

これによって、アプリケーションのコードを書き換えず、実際にLinuxへ到達したシステムコールをもとに副作用を集められます。

また、seccomp user notificationに含まれる[TID](https://man7.org/linux/man-pages/man2/gettid.2.html)と `Thread#native_thread_id` を照合し、取得できる場合はシステムコールを発行したRubyコードのバックトレースも表示します。

Straycallが自動で安全なポリシーを決めるわけではありません。必要なアクセスかどうかはプロジェクトごとに異なるため、実際に発生した副作用を見直すきっかけとして使うことを想定しています。

また、Straycallは悪意のあるコードを閉じ込めるためのセキュリティサンドボックスではありません。前述したTOCTOUなどの制約があるため、テストやビルドへ偶然入り込んだ副作用を検出するための道具として位置付けています。

## Dockerで試す場合

Dockerなどでは、コンテナランタイム側のseccompプロファイルによって `seccomp(2)` が拒否される場合があります。

信頼できる開発用コンテナで動作を確認する場合は、次のようにseccompプロファイルを無効化できます。

```console
docker run --rm \
  --security-opt seccomp=unconfined \
  -v "$PWD:/app" \
  -w /app \
  ruby:3.4 \
  bundle exec rake
```

この指定はコンテナの制限を弱めます。信頼できない処理を安全に実行するための指定ではありません。

## おわりに

`seccomp-notify` は、対象プロセスのシステムコールを実行前に止め、接続先やファイルパスを調べられます。調べた結果に応じて、続行、拒否、戻り値の偽装、ファイルディスクリプタの注入といった応答ができます。

システムコールの監視というと、Rubyのアプリケーション開発からは少し離れた話に見えるかもしれません。しかし、テスト中の外部通信を止める、ビルドが触ろうとしたファイルを確認する、OSとの境界で障害を発生させる、といった形にすると、Rubyの開発でも試せることがありそうだなと思っています。

一方で、seccomp user notificationにはTOCTOUなどの注意点があり、使える機能と安全に保証できることは分けて考える必要があります。Straycallについても、すべての副作用を完全に捕捉したり、自動で安全を保証したりするものではありません。

まだ改善できるところは多いです。Linux上でRubyプログラムが発行しているシステムコールを調べたり、テストやビルドの副作用を見直したりするきっかけとして、使ってもらえると嬉しいです。
