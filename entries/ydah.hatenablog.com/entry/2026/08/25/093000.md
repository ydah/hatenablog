Linuxのseccomp user notificationをRubyから扱う `seccomp-notify` というGemを作りました。

[https://github.com/ydah/seccomp-notify:embed:cite]

このGemを作ったきっかけは、2026年8月22日に開催された[Kernel/VM探検隊@東京 No19](https://kernelvm.connpass.com/event/395390/)で、[@nullpo_head](https://github.com/nullpo-head)さんの「動的にallow/denyできる ファイルサンドボックスを作る」という発表を聞いたことでした。

[https://speakerdeck.com/nullpo_head/deny-dekiru-o-tsukuru:embed:cite]

発表では、Seccomp-BPF、Namespace、LandlockといったLinuxのサンドボックス技術を整理した上で、seccomp user notificationを使ってファイルアクセスの判断を別プロセスへ委譲する仕組みが紹介されていました。

通常のSeccomp-BPFでは、システムコール番号や整数の引数を使って許可や拒否を決められます。一方で、`openat(2)` に渡されたファイルパスや、`connect(2)` に渡された接続先のように、ポインタの先にあるデータをフィルターから読むことはできません。

seccomp user notificationでは、対象のシステムコールを実行前に止め、listener FDを持つ別プロセスへ通知できます。通知を受け取った側は、対象プロセスのメモリなどを調べた上で、システムコールを続行する、エラーを返す、元の処理を実行せずに戻り値を返す、といった応答ができます。監視プロセス側で開いたファイルディスクリプタを対象プロセスへ渡すこともできます。

Rubyから扱えるようにすると、テスト中の外部通信を止めたり、プログラムが開こうとしたファイルを確認したり、OSとの境界で意図的にエラーを返したりできそうです。

そこで、Linuxのseccomp user notificationをRubyから扱うためのBindingとして `seccomp-notify` を作りました。

### seccomp-notifyとは

`seccomp-notify` は、Linuxのseccomp user notificationをRubyから扱うためのGemです。

大きくは以下のことができます。

- 通知または拒否するシステムコールをRubyで指定する
- フィルターを設定した対象プロセスを起動し、監視プロセスをフィルターの外側に残す
- システムコールの通知をRubyのハンドラーで受け取る
- 対象プロセスから文字列、バイト列、ソケットアドレスを読む
- 指定した `errno` を返してシステムコールを失敗させる
- 元のシステムコールを続行する
- 元のシステムコールを実行せず、成功したように戻り値を返す
- 監視プロセス側のファイルディスクリプタを対象プロセスへ渡す
- 利用できるカーネル機能を実行時に確認する

C拡張やlibseccompには依存せず、Ruby標準添付の `Fiddle` からLinuxのカーネルAPIを呼び出しています。現在はLinuxのx86_64とaarch64、Ruby 3.1以降を対象にしています。

ただし、`seccomp-notify` はセキュリティポリシーや完成したサンドボックスではありません。seccomp user notificationには、対象メモリを確認してから元のシステムコールを続行するまでの間にデータが書き換えられるTOCTOUなどの注意点があります。`seccomp-notify` は、この仕組みをRubyから利用するための部品として作っています。

[https://www.kernel.org/doc/html/latest/userspace-api/seccomp_filter.html:embed:cite]

[https://man7.org/linux/man-pages/man2/seccomp_unotify.2.html:embed:cite]

### インストール

インストールは通常のGemと同じです。プロジェクトへ追加する場合は、以下のように追加できます。

```console
bundle add seccomp-notify
```

勿論、グローバルにインストールして使うこともできます。

```console
gem install seccomp-notify
```

基本的なuser notificationにはLinux 5.0以降が必要です。元のシステムコールを続行する `CONTINUE` にはLinux 5.5以降、ファイルディスクリプタの注入にはLinux 5.9以降が必要です。

ただし、カーネルの機能はバックポートされることがあります。また、コンテナランタイムのseccompプロファイルによって、ホストのカーネルが対応していても利用できない場合があります。そのため、`seccomp-notify` はカーネルのバージョン文字列だけではなく、現在の環境で各機能を実際に利用できるか確認します。

### まずシステムコールを止める

分かりやすい例として、`curl` のネットワークアクセスを拒否してみます。

```ruby
require "seccomp/notify"

policy = Seccomp::Notify::Policy.new do
  notify :connect, :sendto
end

supervisor = Seccomp::Notify.spawn(policy) do
  exec("curl", "https://example.com")
end

supervisor.on(:connect) do |request|
  request.error!(Errno::ENETUNREACH)
end

supervisor.on(:sendto) do |request|
  request.error!(Errno::ENETUNREACH)
end

status = supervisor.run
```

`curl` が `connect(2)` または `sendto(2)` を発行すると、カーネルは元のシステムコールを実行する前に対象スレッドを停止します。通知を受け取ったRubyのハンドラーは `ENETUNREACH` を返すため、元のシステムコールは実行されません。

アプリケーションのHTTPクライアントを差し替えているわけではなく、実際にLinuxへ到達したシステムコールを対象にしています。そのため、Rubyのライブラリだけではなく、C拡張や子プロセスから発行されたシステムコールも、フィルターの継承範囲内で対象になります。

`Seccomp::Notify.spawn` では、子プロセスへフィルターを設定し、親プロセスはフィルターの外側に残して通知を処理します。監視プロセスまで同じフィルターの内側へ入れると、通知を処理するために必要なシステムコールまで止めてしまう可能性があるためです。

### 接続先やファイルパスを確認する

すべての `connect(2)` を拒否するだけであれば、通常のSeccomp-BPFでも実現できます。

seccomp user notificationでは、対象プロセスへ渡された `struct sockaddr` を読み、接続先を確認してから応答できます。

```ruby
supervisor.on(:connect) do |request|
  address = request.read_sockaddr(
    request.args[1],
    request.args[2]
  )

  loopback = address.ip? &&
    ["127.0.0.1", "::1"].include?(address.ip_address.split("%", 2).first)

  if loopback
    request.continue!(unsafe: true)
  else
    request.error!(Errno::EPERM)
  end
end
```

この例では、`127.0.0.1` と `::1` への接続だけを続行し、それ以外の接続を拒否しています。IPアドレスだけではなく、ポート番号やUnix domain socketのアドレスを確認することもできます。

同じように、`open(2)` や `openat(2)` の通知から、対象プロセスが開こうとしているパス文字列を読めます。

```ruby
policy = Seccomp::Notify::Policy.new do
  notify :openat
end

supervisor = Seccomp::Notify.spawn(policy) do
  exec(*ARGV)
end

supervisor.on(:openat) do |request|
  path = request.read_string(request.args[1])
  warn "openat: #{path}"
  request.continue!(unsafe: true)
end

supervisor.run
```

これによって、ビルドがどのファイルを開こうとしたかを調べたり、テスト中に想定していない設定ファイルへアクセスしていないか確認したりできます。

`seccomp-notify` は対象プロセスのメモリを読んだ後、通知IDがまだ有効であることを確認します。ただし、通知が有効であることと、読んだメモリの内容がその後も変化しないことは別です。

対象メモリを読んだ後に `continue!` を呼ぶと、別スレッドが検査済みの文字列を書き換えてから元のシステムコールを実行させる可能性があります。`unsafe: true` は、この危険を理解した上で続行することを示し、警告を抑えるための指定です。この指定によって処理が安全になるわけではありません。

### 元のシステムコールを実行せずに応答する

通知されたシステムコールには、主に以下の応答ができます。

- `error!(Errno::EPERM)` は、元のシステムコールを実行せず、指定した `errno` を返す
- `continue!` は、カーネルに元のシステムコールを実行させる
- `allow!(value)` は、元のシステムコールを実行せず、成功した結果として戻り値を返す
- `add_fd!(io)` は、監視プロセス側のファイルディスクリプタを対象プロセスへ渡す
- `kill!` は、通知を発行したプロセスを終了させる

`allow!` は、元のシステムコールをそのまま許可するという意味ではありません。元の処理を実行せず、成功したように戻り値だけを返します。元のシステムコールを実行する場合は `continue!` を使います。

この仕組みを使うと、`connect(2)` に `ETIMEDOUT` を返したり、`openat(2)` に `EACCES` を返したりして、障害時の動作を確認できます。アプリケーションごとのモックを追加せず、OSとの境界で失敗を発生させられます。

もちろん、システムコールの戻り値にはそれぞれ意味があります。成功値を適当に返すと、対象プロセスを不整合な状態にする可能性があります。`allow!` は任意の処理を安全に無視する機能ではなく、戻り値の意味を理解した上でエミュレートするための機能です。

### ファイルディスクリプタを差し替える

seccomp user notificationでは、監視プロセス側のファイルディスクリプタを対象プロセスへ注入できます。

リポジトリには、対象プロセスが `/dev/urandom` を開こうとした場合に、別のファイルを渡す例を置いています。

```ruby
require "seccomp/notify"

replacement = File.expand_path("replacement.bin")
open_syscalls = RUBY_PLATFORM.include?("x86_64") ? %i[open openat] : %i[openat]

policy = Seccomp::Notify::Policy.new do
  notify(*open_syscalls)
end

supervisor = Seccomp::Notify.spawn(policy) do
  exec(*ARGV)
end

handler = proc do |request|
  path_argument = request.syscall == :open ? 0 : 1
  path = request.read_string(request.args[path_argument])

  if path == "/dev/urandom"
    File.open(replacement) do |file|
      request.add_fd!(file)
    end
  else
    request.continue!(unsafe: true)
  end
end

open_syscalls.each do |syscall|
  supervisor.on(syscall, &handler)
end

supervisor.run
```

対象プロセスが `open(2)` または `openat(2)` を発行すると、監視プロセスが代わりに `replacement.bin` を開きます。そのファイルディスクリプタを対象プロセスのFDテーブルへ追加し、対象プロセスには追加されたFD番号を戻り値として返します。

対象プロセスから見るとファイルを開く処理が成功していますが、実際に渡されているのは監視プロセスが用意した別のファイルです。

この機能を使うと、テスト中だけ特定のファイルを固定した内容へ差し替えたり、対象プロセスへ直接ファイルを開かせず、別プロセスが開いたFDを渡したりできます。

[@nullpo_head](https://github.com/nullpo-head)さんの発表で紹介されていたCage Boxでも、Landlockで対象プロセスからのファイルアクセスを制限した上で、ブローカーが代わりにファイルを開き、そのFDを対象プロセスへ注入していました。

[https://github.com/nullpo-head/cage-box:embed:cite]

単にシステムコールを許可または拒否するだけではなく、処理を別のプロセスへ移し、その結果を対象プロセスへ返せるところがseccomp user notificationの特徴です。

### seccomp-notifyを使ってできること

ここまでの機能を組み合わせると、たとえば以下のような用途に使えます。

- 選んだシステムコールを表示する小さなトレーサーを作る
- テスト中の外部ネットワークアクセスを拒否する
- プログラムが渡したファイルパスや接続先を記録する
- 指定した `errno` を返して障害時の動作を確認する
- ファイルやソケットを別のFDへ差し替える
- 対象プロセスの代わりに別プロセスが処理を行うブローカーを作る
- パッケージのインストールやビルド中に発生した副作用を調べる

Bindingとしては、これらを組み立てるための低レベルな機能を提供しています。

### seccomp-notifyを使って作ってみたGemについて

RubyやRailsのアプリケーションでは、テスト中にデータベースへ接続したり、`tmp` や `log` へファイルを書き込んだり、必要なコマンドを子プロセスとして起動したりします。もちろん、それぞれの処理には必要な理由があります。

しかし、依存ライブラリの変更や設定の見落としによって、テスト中に外部サービスへ接続していたり、想定していない場所へファイルを書き込んでいたりすることもあります。また、Gemのインストールやビルドの途中で、意図していないコマンドが実行されている可能性もあります。

こうした副作用は、すぐに大きな問題になるとは限りません。しかし、テストの再現性を下げたり、開発環境の状態へ依存したり、CIから意図しない通信を行ったりする原因になります。

そこで、`seccomp-notify` を使って、実際にLinuxへ到達したシステムコールをもとに、見直した方がよい副作用を集める `Straycall` というGemを作りました。

[https://github.com/ydah/straycall:embed:cite]

Straycallは、Rubyのビルドやテストが発行したシステムコールを監視し、意図していないネットワークアクセス、ファイルアクセス、コマンド実行を報告または拒否するCLIです。

大きくは以下のことができます。

- 新しいネットワーク接続、明示的なUDP送信先、`bind(2)`、`listen(2)` などを検出する
- 許可したホスト、ポート、ファイルシステム上のパスを持つUnix domain socketだけを利用できるようにする
- 選択したファイル書き込みやファイルシステム変更を検出する
- `open(2)` 系で指定したファイルやディレクトリの読み取りを検出する
- `execve(2)` と `execveat(2)` によるコマンド実行を検出する
- 違反した処理を拒否、警告、記録、または対話的に確認する
- システムコールを発行したRubyコードのバックトレースを、取得できる場合に表示する
- RSpecやMinitestのテストケースと違反を関連付ける
- 検出結果をJSONとして保存する

Straycallが自動で安全なポリシーを決めるわけではありません。テスト中に発生したネットワークアクセスやファイル書き込みが必要なものか、意図しないものかは、プロジェクトによって異なります。

Straycallは、実際に発生したアクセスを機械的に集めて、見直す必要がある副作用を確認しやすくするための道具として使えないかなと作ってみました。

### Straycallを使う

基本的な使い方は、監視したいコマンドをStraycallで包むことです。

```console
straycall --config .straycall.yml -- bundle exec rspec
```

たとえば、次のように設定できます。

```yaml
network:
  default: deny
  allow:
    - host: 127.0.0.1
      ports: [5432, 6379]
    - unix: /var/run/postgresql/.s.PGSQL.5432

write:
  default: deny
  allow:
    - tmp
    - log
    - coverage
    - /tmp
  deny_read:
    - "~/.ssh"
    - "~/.aws"
    - "~/.gem/credentials"

exec:
  default: allow
  deny:
    - /usr/bin/curl
    - /usr/bin/wget

on_violation: fail
report_backtrace: true
report_path: tmp/straycall.json
```

この設定では、ネットワークアクセスを原則拒否し、localhostのPostgreSQLとRedis、指定したUnix domain socketへの接続だけを許可しています。

ファイル書き込みは `tmp`、`log`、`coverage`、`/tmp` 以下だけを許可します。また、SSH、AWS、RubyGemsの認証情報を `open(2)` 系で読み取ろうとした場合も違反として扱います。

コマンド実行は原則許可していますが、`curl` と `wget` は拒否します。コマンドを原則拒否した上で個別に許可する場合は、`exec.default` を `deny` にして、`allow` または `allow_under` を設定できます。

ホスト名は設定を読み込む時点で名前解決されます。ファイルシステムのパスは絶対パスへ展開され、実行ファイルのパスは可能な場合にシンボリックリンクを解決して比較します。

### 4つのモード

Straycallでは、違反を検出したときの動作を4種類から選べます。

- `fail` は、システムコールへ `EPERM` を返し、処理を失敗させる
- `warn` は、システムコールを続行しながら警告を表示する
- `record` は、システムコールを続行しながら、観測したアクセスからポリシー候補を作る
- `prompt` は、`/dev/tty` からその場で許可するかどうかを確認する

デフォルトは `fail` です。

既存のテストスイートへ導入する場合は、最初からすべての違反を止めるのが難しいこともあります。その場合は、まず `warn` で実際に発生しているアクセスを確認できます。

```console
straycall --warn -- bundle exec rspec
```

実際に観測したアクセスから設定を作り始める場合は、`record` を使います。

```console
straycall --record -- bundle exec rspec
```

現在の実装では、指定がなければ `.straycall.recorded.yml` へ書き出します。既存ファイルは上書きせず、すでに存在する場合はエラーになります。意図して置き換える場合だけ `--force` を指定します。

`record` が書き出すのは、観測したネットワーク宛先、ファイルシステム上のUnix domain socket、socket domain、listenerの状態、ファイルの書き込みまたは変更先、実行ファイルです。すべてのファイル読み取りを記録し、`deny_read` の候補を自動生成する機能ではありません。

また、生成されたポリシーをそのまま正解として扱うものでもありません。テスト中に外部APIへ接続していたからといって、今後もその接続を許可すべきとは限りません。むしろ、記録されたことで初めて意図しない通信に気づくこともあります。

まず観測結果を集め、必要なアクセスかどうかを人間がレビューする使い方を想定しています。

### Rubyのバックトレースを表示する

カーネルから受け取る通知だけでも、`connect(2)` が発行されたことや、接続先のアドレスは分かります。しかし、それだけではRubyコードのどこを確認すればよいのか分かりません。

Straycallでは、対象プロセス側にレポーター用のRubyスレッドを起動します。seccomp user notificationに含まれるTIDと `Thread#native_thread_id` が一致するRubyスレッドを探し、バックトレースを取得します。

そのため、取得できる場合は、違反したシステムコールと一緒にRubyコード上の発生箇所を表示できます。

```text
straycall: connect(2) → 192.0.2.1:443
    /path/to/project/lib/client.rb:42:in `request'
    /path/to/project/spec/client_spec.rb:18:in `block (2 levels) in <top (required)>'
  hint: allow_host "192.0.2.1", ports: [443]
```

Rubyのバックトレースを取得できない場合は、通知に含まれる命令ポインタと `/proc/<tid>/maps` から、共有ライブラリなどの位置を補助情報として表示します。ネイティブコードや、Ruby以外へ `exec` した子孫について、常にRubyのバックトレースを取得できるわけではありません。

RSpecとMinitest向けの連携も用意しています。

```ruby
# RSpec
require "straycall/rspec"

# Minitest
require "straycall/minitest"
```

これらを読み込むと、現在実行しているテストケースの情報を違反へ関連付けられます。

CLI経由ですでにSupervisorが動いている場合は、そのSupervisorを再利用します。CLIを使わずテストプロセスの中から直接インストールすることもできますが、その時点ですでに存在する別スレッドへ新しいフィルターを適用することはできません。現在の実装は既存スレッドがある場合に警告します。

そのため、テストプロセス全体を同じ条件で監視したい場合は、まずCLIでテストコマンド全体を包み、その上でRSpecまたはMinitest連携を読み込む使い方が分かりやすいと思います。

### Straycallが監視している範囲

Straycallは、プロセスが行うすべてのI/Oを完全に記録するものではありません。現在の実装では、目的に合わせて選んだシステムコールを監視しています。

ネットワークでは、`socket(2)`、`connect(2)`、`bind(2)`、`listen(2)`、`sendto(2)`、`sendmsg(2)`、`sendmmsg(2)` を対象にしています。新しい接続や明示的な送信先は確認できますが、フィルター設定前から存在する接続済みソケットや、既存FDを使った処理は対象外です。

ファイルシステムでは、`open(2)`、`openat(2)`、`openat2(2)` に加えて、削除、rename、mkdir、link、symlink、truncate、chmod、chown、時刻変更、`copy_file_range(2)`、書き込み可能な共有 `mmap(2)` など、選択した変更操作を対象にしています。

ただし、フィルター設定前から存在する書き込み可能なFDに対するすべての `write(2)` を監視しているわけではありません。対応していないファイルシステム操作もあります。そのため、あらゆるファイル書き込みを完全に列挙するものではないです。

コマンド実行では、`execve(2)` と `execveat(2)` を対象にしています。また、監視漏れを減らすため、Straycallは `ptrace(2)` と新しい `io_uring` を作る `io_uring_setup(2)` をデフォルトで拒否します。ただし、フィルター設定前から存在する `io_uring` などは対象外です。

このように、Straycallは対象とするシステムコールを広げていますが、Linux上のすべての副作用を完全に捕捉するものではありません。

### セキュリティサンドボックスではない

Straycallは、悪意のあるコードを閉じ込めるためのセキュリティサンドボックスではありません。

seccomp user notificationで対象プロセスのメモリからパスや接続先を読み、その後で `CONTINUE` を返す場合、検査してから実際にシステムコールが実行されるまでに対象のメモリが書き換えられる可能性があります。

```text
supervisor                    targetの別スレッド

パスを読む
  |
  |                           パス文字列を書き換える
  v
CONTINUE
  |
カーネルが元のシステムコールを実行する
```

`SECCOMP_IOCTL_NOTIF_ID_VALID` は、通知がまだ有効かどうかを確認するためのものです。検査した文字列がその後も同じ内容であることまでは保証しません。

さらに、Straycallのファイルパス判定は、対象のcwdまたはdirfdを `/proc` から取得し、文字列としてパスを展開して行います。シンボリックリンクを解決して、実際に到達するファイルが許可ルート内にあることを保証するものではありません。

既存のファイルディスクリプタ、既存のソケット、共有メモリ、vDSO、既存の `io_uring`、直接インストールした時点ですでに存在するスレッドなど、seccomp user notificationだけでは完全に制御できないものもあります。

Straycallが対象にしているのは、テストやビルドへ偶然入り込んだ副作用です。外部通信していることに気づいていなかった、想定していない場所へ書き込んでいた、といった事故を検出するための道具として位置付けています。

一方、[@nullpo_head](https://github.com/nullpo-head)さんの発表で紹介されていたCage Boxでは、Landlockによって対象プロセスのファイルアクセスをカーネル側で制限し、その上でブローカーが実際に開いたファイルのFDを対象プロセスへ渡します。

[https://docs.kernel.org/userspace-api/landlock.html:embed:cite]

同じseccomp user notificationを利用していても、Straycallとは目的と構成が異なります。意図しない処理を見つけるための道具と、敵対的なコードを制限するためのサンドボックスは、分けて考える必要があります。

### 実装について

この記事では、`seccomp-notify` を使って何ができるかを中心に紹介しましたが、実装についても少しだけ触れておきます。

`seccomp-notify` はRuby標準添付の `Fiddle` から `seccomp(2)`、`prctl(2)`、`ioctl(2)`、`poll(2)` などを呼び出しています。カーネルとやり取りする構造体は、Rubyの `String#pack` と `String#unpack` で表現しています。

通知対象を選ぶcBPFプログラムもRubyで生成しています。フィルターの先頭でアーキテクチャを確認し、x86_64ではx32 ABIのシステムコールを拒否します。`openat(2)` の書き込みフラグなど、整数引数で絞り込めるものは、ユーザー空間へ通知する前にcBPF側で確認できます。

対象プロセスがフィルターを設定して取得したlistener FDは、Unix domain socketの `SCM_RIGHTS` を使って監視プロセスへ渡します。また、カーネルが対応している `CONTINUE` やFD注入などの機能を、隔離した子プロセスで実際に試して検出しています。

Bindingの実装について詳しく書くと、とんでもない分量になりそうなので、この程度にしておきます。

### Dockerで試す場合

Dockerなどでは、コンテナランタイム側のseccompプロファイルによって `seccomp(2)` が拒否される場合があります。

信頼できる開発用コンテナで動作を確認する場合は、次のようにseccompプロファイルを無効化できます。

```console
docker run --rm \
  --security-opt seccomp=unconfined \
  -v "$PWD:/app" \
  -w /app \
  ruby:3.4 \
  bundle exec rake
```

この指定はコンテナの制限を弱めます。信頼できない処理を安全に実行するための指定ではありません。

また、StraycallはLinuxかつMRIで、seccomp user notificationと `CONTINUE` が利用できる場合に監視を行います。非対応環境や `STRAYCALL=0` の場合は、対象コマンドを監視せず通常どおり実行します。

CIで必ず監視を有効にしたい場合は、コマンドが実行できたことだけではなく、Straycallが監視可能な環境で動いていることも確認する必要があります。

### おわりに

`seccomp-notify` は、Linuxのseccomp user notificationをRubyから扱うためのGemです。
対象プロセスのシステムコールを実行前に止め、接続先やファイルパスを調べ、続行、拒否、戻り値の偽装、ファイルディスクリプタの注入といった応答ができます。

システムコールの監視というと、Rubyのアプリケーション開発からは少し離れた話に見えるかもしれません。しかし、テスト中の外部通信を止める、ビルドが触ろうとしたファイルを確認する、OSとの境界で障害を発生させる、といった形にすると、Rubyの開発でも試せることがありそうだなと思っています。

一方で、seccomp user notificationにはTOCTOUなどの注意点があり、使える機能と安全に保証できることは分けて考える必要があります。Straycallについても、すべての副作用を完全に捕捉したり、自動で安全を保証したりするものではありません。

まだ改善できるところは多いですが、Linux上でRubyプログラムがどのようなシステムコールを発行しているのかを調べたり、テストやビルドの副作用を見直したりするきっかけとして使ってもらえると嬉しいです。
